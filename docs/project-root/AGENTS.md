# AGENTS.md — 프로젝트 공통 에이전트 작업 규칙

이 파일은 Codex, Claude Code, 기타 코딩 에이전트가 이 저장소에서 작업할 때 반드시 따르는 프로젝트 기준 문서다.  
목표는 **기능 회귀**, **지시 누락**, **불필요한 수정**, **검증 없는 완료 선언**을 줄이고, Unity 게임 개발 및 일반 프로그램 개발에서 상업용 수준의 결과물을 안정적으로 만드는 것이다.

---

## 0. 최우선 운영 원칙

1. 사용자의 이번 작업 지시가 최우선이다.
2. 그다음 이 `AGENTS.md`의 코어 규칙을 따른다.
3. 작업 성격에 맞는 Skill 규칙을 추가 적용한다.
4. 프로젝트의 기존 구조, 네이밍, 아키텍처, 테스트 관행을 따른다.
5. 일반적인 베스트 프랙티스는 위 규칙과 충돌하지 않을 때만 적용한다.

충돌이 있으면 임의로 섞지 말고, 더 좁은 범위의 명시 지시를 우선한다.

---

## 1. 기본 코드 작성 규칙

1. MVVM 패턴과 OOP를 적극적으로 사용하되, 프로젝트 기존 아키텍처를 우선한다.
2. **결합도는 낮추고 응집도는 높인다.** 모듈 간 의존성을 줄여 유지보수성과 재사용성을 높인다.
3. 필요 이상의 수정은 금지한다. 정상 동작 중인 기존 기능을 건드려 회귀를 만들지 않는다.
4. 코드는 클린 코드 원칙을 따르며 간결하고 단순하게 작성한다. 단, “짧은 코드”보다 “정상 동작과 유지보수성”을 우선한다.
5. 복잡한 기능, 리팩터링, UI/UX 변경, 게임플레이 변경은 먼저 작업지시서 수준의 계획을 세운다. 사용자가 “바로 작업”을 명시한 경우만 예외다.
6. 주석은 필요한 경우에만 작성하고, 반드시 간결한 한국어로 작성한다.
7. 자료구조와 알고리즘을 적절히 사용해 데이터를 체계적이고 효율적으로 다룬다.
8. 사용자에게 보이는 UI 문구는 한국어를 우선한다. 필요한 기술 용어는 영어 병기 가능하다. 이모티콘은 사용하지 않는다.
9. 기능을 추가하거나 삭제할 때는 연결된 UI, 상태, 테스트, 저장 구조, 오류 처리, 문서, 하네스까지 함께 고려한다.

## 2. Engineering Quality Rules

### E1. 변경 의도 1개 원칙
한 번의 작업은 하나의 목적을 유지한다. 기능 추가, 버그 수정, 리팩터링, 성능 개선을 가능하면 분리한다.

### E2. 기존 컨벤션 최우선
디렉터리 구조, 네이밍, 레이어 분리, DI, 상태 관리, 에러 처리 방식은 기존 프로젝트 패턴을 따른다. 새 패턴이나 새 라이브러리는 근거와 대안이 있을 때만 도입한다.

### E3. 명시적 에러 처리
예외를 조용히 삼키지 않는다. 상위 전파, 사용자/호출자에게 의미 있는 결과 변환, 안전한 대체 경로 중 하나를 선택한다.

### E4. 경계 검증
외부 입력, 네트워크, 파일, 유저 입력, 환경변수, 저장 데이터는 경계에서 검증·정규화한다.

### E5. 타입 안정성과 불변성 우선
Nullable, dynamic, Any 남발을 피한다. 가능한 범위에서 불변 데이터와 명시적 상태 모델을 사용한다.

### E6. 테스트 동반 원칙
신규 로직과 버그 수정에는 가능한 한 테스트를 추가한다.

- 버그 수정: 재현 테스트 또는 회귀 테스트 우선
- 신규 로직: 핵심 비즈니스 로직 단위 테스트 우선
- 상태 기반 기능: 상태 전이 테스트 우선
- Unity: 순수 로직은 EditMode, 런타임/씬/상호작용은 PlayMode 또는 수동 QA

### E7. 품질 게이트
빌드, 타입체크, 린트, 포맷, 테스트가 실패하면 완료로 보고하지 않는다. 실행할 수 없는 환경이라면 실행하지 못한 이유와 수동 검증 절차를 남긴다.

### E8. 의존성 최소화
새 라이브러리는 표준 라이브러리 또는 기존 의존성으로 해결이 어려울 때만 추가한다. 도입 시 이유, 대안, 성능, 보안, 라이선스 영향을 남긴다.

### E9. 관측 가능성
장애 분석에 필요한 최소 로그, 에러 코드, 컨텍스트를 남긴다. 개인정보와 민감정보는 로그에 포함하지 않는다.

### E10. 배포/롤백 안전
스키마, 저장 포맷, 캐시, 프로토콜 변경은 backward-compatible를 우선한다. 위험한 변경에는 롤백 전략을 남긴다.

## 3. 상업용 퀄리티 기준

이 프로젝트의 목표는 “데모가 된다”가 아니라 **유료 상업용 제품처럼 느껴지는 결과물**이다.

작업 시 다음을 검토한다.

- 기능 정확성
- 상태 완전성
- UX 흐름과 피드백
- 실패/복구 경로
- 성능 민감 구간
- 접근성
- 유지보수성
- 테스트 가능성
- 회귀 위험
- 롤백 포인트

“작동한다”에서 멈추지 않는다. 필요한 경우 Loading, Empty, Error, Disabled, Retry, Cancel, Undo, Recovery 상태를 정의한다.

## 4. Skill Routing

작업 성격에 따라 다음 Skill을 추가 적용한다.

### 4.1 상업용 제품 품질 작업
적용 Skill:

- `commercial-grade-product`

사용 조건:

- 기능 구현이 상업용 수준의 완성도를 요구할 때
- 게임플레이, UI, SaaS, 관리자툴, 유틸리티 등 사용자가 실제로 쓰는 결과물을 만들 때
- 단순 구현이 아니라 UX, 견고성, 성능, 접근성, QA까지 확인해야 할 때

### 4.2 UI/UX 작업
적용 Skill:

- `uiux-implementation`

사용 조건:

- 화면, 컴포넌트, 폼, 내비게이션, 반응형, 다크모드, 접근성, 리스트/이미지 성능 작업

필수 검토 상태:

- Loading
- Success
- Empty
- Error
- Disabled

### 4.3 Unity 회귀 검증 작업
적용 Skill:

- `unity-regression-check`
- `unity-verify`

사용 조건:

- Unity 게임 기능 추가/수정
- 씬, UI, 게임플레이, 전투, 입력, 카메라, 저장, 전환 흐름 변경

### 4.4 계속 진행 루프
적용 Skill:

- `continuous-dev-loop`

사용 조건:

- 사용자가 “계속 진행해”, “이어서 진행해”, “서브에이전트 활용해서 계속해”, “Unity에서 구현하고 스크린샷 비교하면서 계속해”라고 지시할 때
- 아래 긴 반복 프롬프트와 유사한 내용을 말할 때

## 5. 긴 반복 프롬프트 자동 해석 규칙

사용자가 다음 문장 또는 유사 문장을 말하면, 일반적인 큰 작업 요청이 아니라 **`CONTINUOUS_DEV_LOOP` 실행 요청**으로 해석한다.

> 계속해서 작업 이어서 진행하고 서브에이전트 활용해서 최대한 같이 작업 가능한 부분들은 같이 작업해서 크게크게 효율적으로 개발했으면 하고 전체작업 진행도와 현재 작업 진행도, 남은 작업들이 어떤게 있는지도 계속해서 정리 및 업데이트해서 브리핑해줘. 그리고 어느정도 정리가 된 애들은 직접 유니티상에서 구현하면서 직접 테스트 하는 과정도 진행해줘. 유니티에서 구현한 스크린샷이랑 갓필드 사이트의 개발중인 창 스크린샷이랑 비교하며 분석하면서 개발해.

동일하게 해석할 짧은 트리거:

- 계속 진행해
- 이어서 진행해
- 진행상황 업데이트하면서 계속해
- 서브에이전트 활용해서 계속해
- Unity에서 구현하고 테스트하면서 계속해
- 스크린샷 비교하면서 계속해
- 다음 미완료 작업 계속 처리해

### CONTINUOUS_DEV_LOOP 실행 절차

1. 먼저 이 파일과 프로젝트 `CLAUDE.md`를 읽는다.
2. `docs/tasks/*`에서 현재 작업 계약서를 찾는다.
3. `docs/progress/*`에서 현재 진행상태판을 찾는다.
4. 다음 미완료 체크포인트 1개를 선택한다.
5. 수정 전 변경 예정 파일과 검증 전략을 짧게 제시한다.
6. 실제 구현은 메인 에이전트 1개가 수행한다.
7. 서브에이전트는 분석, 리뷰, 검증 용도로만 사용한다.
8. 테스트, 하네스, 수동 QA 중 가능한 검증을 수행한다.
9. 필요 시 Unity 스크린샷과 레퍼런스 스크린샷을 비교한다.
10. 진행상태 파일을 업데이트한다.
11. 전체 진행률, 이번 진행률, 남은 작업, 리스크를 브리핑한다.

중요: 매번 전체 프로젝트를 다시 계획하지 않는다. 진행상태 파일 기준으로 다음 미완료 체크포인트만 처리한다.

## 6. Godfield 스타일 훈련모드 작업 전용 규칙

프로젝트에 `docs/tasks/godfield-training-mode.md`가 있거나, 사용자가 갓필드/God Field/Godfield UI/훈련모드 전투를 언급하면 이 규칙을 적용한다.

### 목표

- 갓필드 사이트의 UI/UX와 진입 단계를 참고해 Unity 안에 유사한 경험 흐름을 구현한다.
- 구현 대상은 **훈련모드 전용 전투**다.
- 다른 플레이어와 엮이지 않는 로컬/훈련 전용 구조를 만든다.

### 저작권/브랜드 주의

- 레퍼런스의 흐름, 정보 구조, 화면 위계, 사용감은 참고한다.
- 외부 서비스의 로고, 고유 이미지, 브랜드 자산, 저작권 리소스를 그대로 복제하지 않는다.
- 프로젝트 고유 리소스와 자체 UI 컴포넌트로 구현한다.

### 절대 금지

- 1:1 모드 구현/연결/수정 금지
- PvP 구현 금지
- 매칭 시스템 구현 금지
- 멀티플레이 연결 금지
- 다른 플레이어와 연결되는 코드 작성 금지
- 모드 선택 화면에서 다른 모드로 진입하는 흐름 구현 금지
- 기존 멀티플레이/네트워크 코드 수정 금지
- 훈련모드 밖의 기능을 임의로 리팩터링 금지

### 허용 범위

- 훈련모드 진입 UI
- 훈련모드 전용 전투 화면
- 로컬 더미 상대 또는 로컬 AI 상대
- 전투 연출, 카드/행동 선택, 턴 진행, 결과 피드백
- Unity 구현 스크린샷 저장
- 레퍼런스 스크린샷과 Unity 구현 스크린샷 비교
- 훈련모드 전용 테스트와 수동 QA

### 필수 문서

작업 시작 전 다음 파일을 우선 확인한다.

1. `docs/tasks/godfield-training-mode.md`
2. `docs/progress/godfield-training-progress.md`

파일이 없으면 먼저 생성 제안을 하거나, 가능한 경우 생성한다.

## 7. 서브에이전트 사용 규칙

“서브에이전트를 활용해서 크게크게 효율적으로”라는 요청은 아래처럼 해석한다.

| 역할 | 목적 | 파일 수정 |
|---|---|---|
| reference-ui-analyst | 레퍼런스 UI/UX, 화면 위계, 진입 흐름 분석 | 금지 |
| unity-architecture-planner | Unity 씬/스크립트 구조 탐색 | 금지 |
| mode-isolation-reviewer | 1:1/PvP/매칭/멀티플레이 침투 여부 검사 | 금지 |
| visual-qa-reviewer | Unity 스크린샷과 레퍼런스 비교 | 금지 |
| test-harness-runner | 하네스/테스트 실행과 결과 요약 | 제한적 |
| main implementer | 실제 구현 | 허용 |

원칙:

- 여러 에이전트가 같은 파일을 동시에 수정하지 않는다.
- 병렬화는 분석/검증/리뷰에 사용한다.
- 실제 코드 수정은 메인 에이전트 1개가 수행한다.
- 서브에이전트 결과는 요약으로 통합하고, 구현 전 충돌 여부를 확인한다.

## 8. 하네스 및 검증 규칙

### Unity 프로젝트

가능한 경우 다음 검증을 사용한다.

- EditMode 테스트: 순수 로직, 상태 전이, 규칙 검증
- PlayMode 테스트: 런타임 동작, 씬 연결, UI 흐름, 전투 흐름
- Smoke 테스트: 핵심 진입 플로우와 주요 상호작용
- 금지 조건 검사: 1:1/PvP/매칭/멀티플레이 연결 여부
- 스크린샷 비교: 레퍼런스와 Unity 구현 화면 비교

권장 산출물:

- `artifacts/harness/last-verify.json`
- `artifacts/screenshots/*.png`
- `docs/progress/*.md`

### 일반 프로그램

가능한 경우 다음 검증을 사용한다.

- lint
- typecheck
- unit test
- integration test
- smoke test
- 수동 QA 체크리스트

실제 실행이 불가능하면 “미실행”이라고 명확히 밝히고, 실행 명령과 예상 결과를 남긴다.

## 9. 작업 진행 방식

### 기본 루프

1. Plan: 목표, 변경 범위, 예상 파일, 검증 전략을 정한다.
2. Patch: 승인된 범위만 수정한다.
3. Verify: 테스트/하네스/수동 QA를 실행한다.
4. Update: 진행상태 문서와 필요 문서를 업데이트한다.
5. Report: 변경 내용, 검증 결과, 남은 작업, 리스크를 보고한다.

### 긴 작업의 끊기 규칙

작업이 오래 걸리거나 산으로 가면 즉시 아래 형식으로 멈추고 정리한다.

1. 실제 변경 파일
2. 각 파일의 변경 내용
3. 성공한 검증
4. 실패한 검증
5. 막힌 지점
6. 다음에 해야 할 최소 작업 1개
7. 되돌려야 할 변경 여부

## 10. 표준 보고 형식

큰 작업 또는 CONTINUOUS_DEV_LOOP 작업 후 반드시 아래 형식으로 보고한다.

```md
## 진행 브리핑

### 전체 진행률
- 0~100%

### 현재 마일스톤
- 현재 진행 중인 마일스톤

### 이번 턴 완료
- 완료한 항목

### 변경 파일
- `path/to/file`

### 검증 결과
- 실행한 테스트/하네스/수동 QA
- 미실행 항목과 이유

### 스크린샷 비교
- 레퍼런스 스크린샷:
- Unity 구현 스크린샷:
- 주요 차이:
- 다음 개선:

### 남은 작업
1. 다음 작업
2. 다음 작업
3. 다음 작업

### 리스크/롤백 포인트
- 리스크
- 롤백 포인트
```

## 11. 금지 행동

- 정상 동작 중인 기능을 근거 없이 수정하지 않는다.
- 완료 조건을 충족하지 않았는데 완료라고 말하지 않는다.
- 테스트를 실행하지 않고 “정상 동작”이라고 단정하지 않는다.
- 외부 의존성을 이유 없이 추가하지 않는다.
- 여러 기능을 한 번에 섞어 리팩터링하지 않는다.
- Godfield 훈련모드 작업 중 1:1/PvP/매칭/멀티플레이를 구현하거나 연결하지 않는다.
- 진행상태 파일을 업데이트하지 않고 “계속 진행했다”고 말하지 않는다.

## 12. 빠른 프롬프트 해석

사용자가 아래처럼 말하면:

```text
계속 진행해.
```

다음 의미로 처리한다.

```text
AGENTS.md, docs/tasks/*, docs/progress/*를 읽고 다음 미완료 체크포인트 1개를 구현한다. 검증 후 progress 파일을 업데이트하고 진행 브리핑을 제공한다.
```

사용자가 아래처럼 말하면:

```text
유니티에서 구현하고 스크린샷 비교하면서 계속해.
```

다음 의미로 처리한다.

```text
Unity 구현 단계로 진입하되, 레퍼런스 스크린샷과 Unity 스크린샷 비교 결과를 progress와 브리핑에 포함한다.
```

사용자가 아래처럼 말하면:

```text
서브에이전트 활용해서 크게크게 진행해.
```

다음 의미로 처리한다.

```text
서브에이전트는 분석/검증/리뷰에 사용하고, 실제 코드 수정은 메인 에이전트 하나가 수행한다.
```

## 13. 작업 이력, 피드백, QR 체크리스트, 자체 자동 테스트

## 작업 시도 이력 · 사용자 피드백 · QR 체크리스트 · 자동 검증 공통 규칙

이 섹션은 모든 프로젝트에서 기능 회귀, 지시 누락, 같은 실패 반복, 장기 작업의 문맥 손실을 줄이기 위한 공통 운영 규칙이다.

### 1. Attempt Ledger: 시도한 방법과 결과 기록

작업 중 의미 있는 시도, 실패, 성공, 보류, 되돌림이 발생하면 프로젝트에 다음 문서를 유지한다.

- `docs/ai-worklog/attempt-log.md`

각 항목은 아래 정보를 포함한다.

| 항목 | 설명 |
|---|---|
| 날짜/작업 ID | 작업을 구분할 수 있는 날짜 또는 짧은 ID |
| 목표 | 무엇을 해결하려 했는지 |
| 시도한 방법 | 실제 적용한 접근법 |
| 결과 | 성공 / 실패 / 부분 성공 / 보류 / 롤백 |
| 근거 | 테스트, 빌드, 스크린샷, 로그, 사용자 확인 등 |
| 실패 원인 | 실패 또는 부분 성공이면 원인 가설 |
| 다음 조치 | 반복하지 않기 위한 다음 액션 |
| 사용자 피드백 | 사용자가 준 평가, 수정 요구, 선호 |

중요: 같은 실패를 반복하지 않도록 새 작업 시작 전 관련 attempt-log를 먼저 확인한다.

### 2. User Feedback Ledger: 사용자 피드백 누적

사용자의 피드백, 선호, 금지 조건, 반복 지적은 다음 문서에 누적한다.

- `docs/ai-worklog/user-feedback.md`

사용자 피드백은 단순 대화 기록이 아니라 다음 작업에 영향을 주는 운영 지식으로 정리한다.

예:

```md
## 2026-04-20 / Godfield UI
- 피드백: 진행률과 남은 작업 브리핑을 매 턴 유지할 것.
- 적용 규칙: CONTINUOUS_DEV_LOOP 보고 형식에 전체 진행률/현재 진행률/남은 작업 포함.
- 상태: 적용 중
```

### 3. 중복 내용 병합 규칙

문서가 길어지거나 같은 내용이 반복되면 다음 원칙으로 병합한다.

1. 같은 금지 조건, 완료 조건, 테스트 명령은 하나의 정본 위치로 합친다.
2. 중복된 지시가 있으면 더 구체적이고 최신인 항목을 남긴다.
3. 오래된 시도 내역은 삭제하지 말고 `docs/ai-worklog/archive/` 또는 압축 요약으로 이동한다.
4. 규칙이 충돌하면 사용자 최신 지시 > 프로젝트 `AGENTS.md` > skill > 일반 관행 순으로 판단한다.
5. 병합 시 “무엇을 병합했고 무엇을 삭제/이동했는지”를 attempt-log에 남긴다.

### 4. 컨텍스트 압축 규칙

다음 중 하나에 해당하면 컨텍스트 압축을 수행한다.

- `attempt-log.md`가 너무 길어져 현재 작업 판단에 방해될 때
- 같은 내용이 3회 이상 반복될 때
- 장기 작업에서 진행상태가 흩어졌을 때
- 에이전트가 이미 완료한 항목을 다시 계획하거나 반복할 때

압축 산출물은 다음 파일이다.

- `docs/ai-worklog/context-summary.md`

압축 요약은 아래 구조를 따른다.

```md
# Context Summary

## 현재 목표

## 반드시 지켜야 할 금지 조건

## 완료된 항목

## 실패했던 접근과 반복 금지 이유

## 사용자 피드백 반영 사항

## 현재 열려 있는 리스크

## 다음 미완료 체크포인트
```

압축 후에는 새 작업 시작 시 전체 긴 로그보다 `context-summary.md`를 먼저 읽는다.

### 5. QR 체크리스트: Quality Review Checklist

여기서 QR은 Quality Review를 의미한다. 작업 완료 전 다음 문서를 사용한다.

- `docs/qa/QR_CHECKLIST.md`

최소 확인 항목:

- 요구사항을 빠뜨리지 않았는가?
- 수정 범위를 벗어나지 않았는가?
- 기존 정상 기능을 건드리지 않았는가?
- 금지 조건을 위반하지 않았는가?
- 테스트/빌드/린트/수동 QA를 실행했는가?
- 실행하지 못한 검증은 이유와 명령을 남겼는가?
- 사용자 피드백을 반영했는가?
- 같은 실패를 반복하지 않았는가?
- 필요한 경우 attempt-log, user-feedback, context-summary를 업데이트했는가?

### 6. 자체 자동 테스트 규칙

가능한 프로젝트에서는 다음 스크립트를 둔다.

- `scripts/harness/auto_self_test.ps1`

에이전트는 작업 완료 전 가능한 범위에서 이 스크립트를 실행한다. 실행하지 못하면 “미실행”이라고 밝히고, 이유와 수동 검증 절차를 남긴다.

자동 테스트는 최소한 다음을 확인한다.

1. 필수 문서 존재 여부
2. QR 체크리스트 존재 여부
3. attempt-log/user-feedback/context-summary 존재 여부
4. 프로젝트별 테스트 명령 실행 가능 여부
5. 금지 키워드 또는 금지 경로 침범 여부
6. 최근 작업 결과 파일 또는 검증 산출물 존재 여부

### 7. 보고 형식 추가

작업 종료 보고에는 기존 보고 형식에 아래 항목을 추가한다.

```md
### 시도/피드백 업데이트
- attempt-log 업데이트: 예/아니오, 이유
- user-feedback 업데이트: 예/아니오, 이유
- context-summary 업데이트: 예/아니오, 이유

### QR 체크리스트
- 통과:
- 실패/미확인:
- 자동 테스트 결과:
```
